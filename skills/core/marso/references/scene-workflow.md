# Complete a scene request

Use this when the user requests a built/reconstructed scene, not just an inventory or a detection viewer. For a text brief without photographs, build a direct asset/placement plan; skip image decomposition and do not manufacture detected graph ids. Graph-dependent helpers require real inputs; verified application controls can implement a direct plan. Retain the original requested outcome across specialist handoffs. Discover installed companions by name; never assume sibling files exist.

For reference photographs, default to the installed decomposition and scene-graph skills, then build and place through Blender. Marso's built-in Detect Objects tool is optional when requested or useful; it is not a required cloud stage before local decomposition. Convert any tool detections into the same reviewed identity/support/route plan rather than treating boxes as a finished scene graph.

## Keep one record

Use one run folder for graph, asset plan, choices, references, generation records, imports and placement. Record the relevant Studio project id, selected routes, user preferences, provisional scene budget, approvals and unresolved items. Resume from observed records; never repeat an uncertain submission or overwrite an active run to advance a stage.

## Stage ownership

| Stage | Owner when installed | Exit evidence |
| --- | --- | --- |
| Inventory from photographs | `marso-scene-decompose` | Validated graph, identity uncertainty and local interactive viewer |
| Unique assets, routes, instances, budget and briefs | `marso-scene-graph` | Reviewed plan and references for all selected routes |
| Existing assets | `marso-library` | Chosen source ids and reusable geometry/materials |
| Generated scene props | `marso-blender-scene-assets` | Native batch/legacy records, actual outputs and review state |
| Modelled assets, architecture, kit parts | `marso-blender-asset` / `marso-blender-kit` | Geometry in the scene with stable plan/entity mapping |
| Requested appearance images or edited style references | `marso-image` | Inspected image/crop with compatible shape and regions, realistic detail at actual returned resolution, and a concise appearance handoff |
| Import, support and placement | `marso-blender-place-scene` | All selected views accounted for, editable Empty/geometry hierarchy |
| Finish visible furniture and props | `marso-blender-texture` | Applied, inspected appearance and saved texture dependencies |
| Performance and requested rendering | `marso-blender-render` | Measured settings/instancing decisions and requested images |

A mixed plan stays mixed: never pass model/kit/instance choices into a generation batch. Modelled assets and room-shell anchors need their own handoff; placeholders are unresolved work. Generation completion alone is not scene completion. Do not retexture a generated or reused asset whose existing appearance already meets the brief.

Before repeating a master, inspect representative source crops and the model's defining proportions/construction. Category labels and a complete graph do not establish shape compatibility or visual quality. An included child still needs an appropriate creation route: food inside a modelled container may need generated or reused geometry. "Part of its parent" is not permission to replace difficult visible contents with crude primitives.

For a new appearance method, establish the quality target before the pilot and retain it through review. Check the source image, then the final Retexture → PBR material, before expanding dependent styles. Technical success with unresolved visual defects is a diagnostic result, not a quality pass. Continue independent accepted work, but do not quietly lower the target to "recognisable at a distance" to justify scaling. These are internal checks, not extra user approvals for every item; keep explicit user-approved approximations distinguishable from method acceptance.

## Continue without redundant handoff questions

Decomposition is a standalone deliverable when that is all the user requested. Within a full-scene request, continue directly to planning; do not offer to start the work already requested. Continue similarly between planning, creation and placement while honouring actual review gates.

Consolidate the asset-plan, library choices and scene-budget review. An earlier approval of unchanged decisions remains valid; review only newly discovered candidates, ambiguities or scope changes. Establish preferred generation options once, then reuse compatible preferences. Do not repeatedly interview the user for each asset.

Show image/mesh reviews for native generation batches unless explicitly waived. Newly modelled or substantially remodelled geometry needs user approval before Retexture/PBR unless waived. Existing unchanged assets requested for retexture need no extra model gate. A finished-scene request alone does not waive these reviews. Record user approval, explicit waiver and agent decisions distinctly.

Native batches own cloud-stage monitoring and advancement. Follow their paginated status and handle review/held states; do not duplicate their jobs in a legacy loop. Continue independent approved work while other items await review. No server-side dependency trigger or chat wakeup is assumed.

## Finish to the requested scope

For a finished scene, texture visible furniture/props that still need it, inspect materials and source-photo placement, save the Blender file with dependencies, and show lightweight review images. Final presentation renders require a request. Keep inherited scale under entity Empty transforms; resizing one geometry group must not resize supported neighbours.

List every selected asset as complete, reused, intentionally skipped or unresolved. State visual defects and missing capabilities. If a specialist/command is unavailable, finish independent stages and identify the missing requirement; never claim a complete scene from a graph or boxes.
