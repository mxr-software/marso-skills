# Images through the Blender add-on

Use the established local Blender control connection and the add-on's public commands. Where that connection executes Blender Python, inspect the enabled modules in `bpy.context.preferences.addons` and identify the actual Marso module (it may be `marso` or `bl_ext.<repository>.marso`). Import that module's `bridge.commands`, discover `all_commands()` / entry `describe()` schemas, then use `execute(name, params)`. Do not hard-code the development import path or guess a client-specific tool prefix. Private services and direct backend calls are not a substitute. Return from a Blender tool call after starting a job and poll in later calls; never block Blender's main thread waiting for completion.

## Choose and submit

1. Discover `scene_image_options`. Confirm scene/object generation, image editing, reference roles, prompt limits and selected project. Select the relevant project with `set_save_project`, or create one with `create_studio_project`, using their current schemas; do not leave work in an unrelated default project. After a new Blender session, refresh with `list_studio_projects` before selecting an existing id, then verify `save_to_state`. Save the chosen destination with the working .blend. Track the project id as identity; its display name may change automatically. Capability discovery is not a pricing/approval step.
2. Use `generate_scene_image` with `mode: "scene"` for a room/set concept or `mode: "object"` for an isolated object image. Use `edit_scene_image` for a revision, with `source: {"node_id": "<accepted source node>"}` in that project. Both create a new node; the edit preserves its source. The mutation commands require local control: Agent Connection alone permits only `scene_image_options` and `scene_image_result`.
3. References name exactly one `node_id` in the selected project or `image_path` to a supported local file. Give each a unique `label` and supported `role`: `layout`, `appearance`, `subject`, `style` or `other`. Mention `@label` in the prompt and explain its visual purpose. Use the actual blockout render as layout and the accepted concept as appearance; a generated result is still a design proposal, not a camera/geometry lock.
4. Assign and save a stable `request_id` before submission. Keep the command, exact parameters, project and source/reference revisions. Retain local input files unchanged while pending. Follow the returned job using `get_job`; the add-on polls the service. Use `scene_image_result` to recover the recorded request/output. Confirm the current job has finalized successfully and the request result succeeded; a nested job snapshot stored in the result can lag behind. Do not repeatedly submit to discover completion.
5. Inspect the returned local image at its actual dimensions. Record project/node/execution IDs, expanded prompt, width/height and visual acceptance before downstream work. Image success does not create a mesh, PBR material or Blender object.

Use the returned prompt contract. The inspected 1.13.1 implementation counts 3–16,384 Python characters after reference tokens and automatic introductions expand. Up to four references accept PNG/JPEG/WebP files within the reported size limits (5 MB and 4096 px per side in that build). The add-on expands labels and orders named references for the service; do not manually inject backend asset tokens. Remove redundant wording before shortening material detail. Do not add unsupported aspect, resolution, seed, mask, negative-prompt or camera-lock arguments. Measure output size rather than promising a fixed ratio or exact crop preservation.

## Resume without duplicate work

- Same id and identical request: completed results return from the journal; active requests return their existing job; known submitted runs are followed. Reuse the id to recover a download or polling failure.
- `submission_uncertain`: a run may have started. Keep the same id and inspect/reconcile later. No automatic new id or blind retry loop; a new id can create another run and requires an intentional decision to run again.
- `request_conflict`: the id belongs to different parameters. Recover the original request, or use a new id only for a deliberately new operation.
- Explicit rejection is different from a failed execution. Correct the rejection before retrying; a failed execution remains failed under its id. Do not interpret either as image success.
- An interrupted node/link preparation is not a successful run. In the inspected 1.13.1 build, recovery of a lost node-create response can duplicate a node or adopt another request's blank node at the same canvas position. If preparation fails before a known run, stop and report the request/node evidence for reconciliation; do not automatically resume that preparation or identify ownership by canvas position. This is distinct from following an already known execution or recovering its download. Do not run recovery experiments in a user's production project.

Capability and route checks take precedence over version numbers. Older object-only commands cannot establish scene-mode generation or editing. If local execution is unavailable, explain the missing connection and continue independent planning; execute blockout work only if another authorized local Blender control route is available; do not silently switch to the separate hosted Marso MCP. Keep all request journals and account/project identifiers in the user's local project records, not public skill files.
